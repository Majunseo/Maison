# 주입한 결함 목록 (F · V · N · U)

레지스트리 네 파일에 등록된 **17건**의 증상과 확인 방법을 한곳에 모았다.
레지스트리는 기계가 읽는 자리(정답지 생성)이고, 이 문서는 사람이 읽는
자리다. 증상·재현 절차·확인용 코드 조각은 여기에만 둔다.

| 접두사 | 분야 | 건수 | 레지스트리 |
|---|---|---|---|
| `F` | 기능적 | 4 | `server/bugs/functional.ts` |
| `V` | 입력 검증 | 5 | `server/bugs/validation.ts` + `validation-behavior.ts` |
| `N` | 이동·라우팅 | 3 | `server/bugs/routing.ts` |
| `U` | UI | 5 | `server/bugs/ui.ts` + `src/styles/bugs-ui.css` |

```sh
npm run dev                  # 정상 — 기준선
BUGS_ON=all npm run dev      # 17건 전부
BUG_F2=1 npm run dev         # 한 건만
```

```
GET /api/bugs    지금 켜진 ID 목록
GET /gt.json     정답지 (레지스트리에서 생성한다. 손으로 쓰지 않는다)
```

**한 건씩 켜고 확인한다.** 여러 건을 같이 켜면 F3 과 U4 처럼 겉보기가
같은 것들이 겹쳐서 원인을 가릴 수 없다. 아래 "겹침 주의" 를 참고한다.

**Maison 은 `data-testid` 를 쓰지 않는다.** 아래 코드 조각의 선택자는
실제 마크업에서 확인한 것이다. 테스트용 속성이 있다고 가정하지 않는다.

# F — 기능적 결함

**동작의 결과**가 잘못된 것만 넣는다. 입력값을 거르는 문제는 `V`,
화면 이동은 `N`, 보이는 모양은 `U` 다. 같은 증상이라도 어디서 생겼는지로
분야가 갈린다 — 담기 버튼이 반응하지 않으면 `F`, 담기 버튼이 흐려지지
않아 누를 수 있어 보이면 `U` 다.

## F1 — 위시리스트에서 마지막으로 담은 항목이 빠짐

하트는 채워지고 헤더 배지 숫자도 늘어나는데, 위시리스트 화면의 카드
목록에만 가장 최근 항목이 나오지 않는다. 한 개만 담았다면 "1 piece
saved" 라고 쓰여 있는데 카드가 0개가 된다.

| 봐야 할 곳 | 정상 | 결함 |
|---|---|---|
| 헤더 배지 | 1 | 1 |
| 화면의 "N piece(s) saved" | 1 | 1 |
| 실제 카드 수 | 1 | **0** |

상품 목록이나 상세에서 하트를 눌러 담고 `/wishlist` 로 간다.

```js
document.querySelector('p[aria-live="polite"]')?.textContent   // "1 piece saved"
document.querySelectorAll('article').length                     // 0
```

숫자가 세 군데 있는데 둘은 맞고 하나만 틀리다. 담긴 것 자체는 저장돼
있어서 새로고침해도 배지는 1 로 남는다.

심은 자리: `src/pages/Wishlist.tsx`

## F2 — 장바구니 담기 거짓 성공

`Added to bag` 토스트가 뜨는데 실제로는 담기지 않는다. 헤더 장바구니
배지가 늘지 않고 `/cart` 도 비어 있다. 오류도 없고 화면도 바뀌므로
성공한 것과 구분되지 않는다.

`/product/arc-pendant-light` 에서 `Add to Bag` 을 누른 직후 배지를 본다.

```js
// 배지는 담긴 것이 있을 때만 그려진다. 담은 직후에도 없으면 안 담긴 것이다.
document.querySelector('a[href="/cart"] span')?.textContent ?? "배지 없음"
```

**토스트만 보면 성공이다.** 담겼는지는 배지나 `/cart` 를 봐야 알 수 있고,
그 둘을 맞춰보지 않으면 영원히 정상으로 보인다.

심은 자리: `src/pages/ProductDetail.tsx`

## F3 — 수량 조절 버튼 무반응

상품 상세와 장바구니의 `+` / `-` 를 눌러도 수량이 바뀌지 않는다. 버튼은
눌리고 눌린 표시도 나는데 숫자가 그대로다.

`/product/arc-pendant-light` 의 `Quantity` 에서 `+` 를 누른다.

```js
document.querySelector('span.tabular-nums')?.textContent   // "1" -> "1"
```

**U4 와 겉보기 증상이 같다.** U4 는 비활성 버튼이 흐려지지 않아 누를 수
있어 보이는 표시 문제이고, 이쪽은 누를 수 있는 버튼이 실제로 동작하지
않는 기능 문제다. 원인을 가려낼 수 있는지 보는 자리다.

심은 자리: `src/components/QuantitySelector.tsx`

## F4 — 컬렉션 필터 해제 무반응

컬렉션을 고른 상태에서 `ALL` 을 눌러도 필터가 풀리지 않는다. 전체
목록으로 돌아갈 방법이 없어진다.

`/products?collection=lighting` 에서 `ALL` 을 누른다. 상품이 2개에서
13개로 늘어나야 하는데 그대로다.

```js
document.querySelectorAll('article').length   // 2 -> 2 (정상은 2 -> 13)
```

**이미 `ALL` 인 상태에서 `ALL` 을 누르는 것과 겉보기가 같다.** 그때는
아무 일이 없는 게 정상이다. "지금 필터가 걸려 있었는가" 를 알아야
판정할 수 있다 — 눌렀다는 사실만으로는 판정이 안 된다.

심은 자리: `src/pages/Products.tsx`

# V — 입력 검증 결함

**입력값을 거르는 기준**이 잘못된 것만 넣는다. 받아들여야 할 것을 막거나,
막아야 할 것을 받아들이는 경우다. 받아들인 뒤의 처리가 틀린 것은 `F` 다.

다섯 건은 과거 번호(V3·V6·V7·V9·V11)에서 V1~V5 로 다시 매긴 것이다.
레지스트리의 `title` 에 `BUG-00n` 과 과거 번호가 같이 적혀 있다.

## V1 — 주문 이메일 형식 검증 누락 (BUG-001, 과거 V3)

형식이 잘못된 이메일로 주문이 접수된다. `/checkout` 에서 다른 필수값은
정상으로 채우고 이메일만 `invalid-address` 로 제출한다. 거부되지 않고
주문이 생성된다.

심은 자리: `src/pages/Checkout.tsx`

## V2 — 계정 이름 공백 저장 (BUG-002, 과거 V6)

이름을 스페이스 3개로 저장하면 받아들여지고, 다시 조회하면 이름이
비어 있다. 저장 단계에서 공백을 다듬지 않아 빈 값 검사를 통과한다.

로그인 후 `/account` 에서 이름을 스페이스 3개로 저장하고 새로고침한다.

```ts
// server/bugs/validation-behavior.ts
return isOn("V2") ? name : name.trim();
```

심은 자리: `server/bugs/validation-behavior.ts`

## V3 — 배송 도시 빈값 수용 (BUG-004, 과거 V7)

도시를 비워도 주문이 접수된다. `/checkout` 에서 이메일과 나머지 필수값을
정상으로 채우고 `City` 만 비워 제출한다.

심은 자리: `src/pages/Checkout.tsx`

## V4 — 재설정 암호 확인 불일치 수용 (BUG-005, 과거 V9)

확인값이 달라도 첫 번째 암호로 재설정된다. 새 유효 링크에서
`FirstPass!123` / `OtherPass!456` 을 넣고 제출하면 통과하고, 이후
`FirstPass!123` 으로 로그인된다.

심은 자리: `src/pages/ResetPassword.tsx`

## V5 — 정확히 8자인 가입 암호 거부 (BUG-003, 과거 V11)

8자 암호가 `weak_password` 로 거부된다. 경계가 `< 8` 에서 `<= 8` 로
한 칸 밀렸다. `/signup` 에서 새 이메일·정상 이름·`Ab12!xyz` 로 가입한다.

```ts
// server/bugs/validation-behavior.ts
return isOn("V5") ? password.length <= 8 : password.length < 8;
```

**이 건은 응답이 스스로 모순된다.** 8자를 거부하면서 같은 응답에
최소 길이가 8이라고 싣는다.

```
POST /api/signup  ->  400 { "error": "weak_password", "minLength": 8 }
```

게다가 같은 사이트의 다른 두 곳은 8자를 받아들인다 — 비밀번호 변경과
재설정은 `password.length < 8` 그대로다(`server/api.ts` 의 347행·408행
부근). **같은 규칙이 화면마다 다르게 적용되는 상태**라, 두 엔드포인트를
비교하면 어느 쪽이 틀렸는지까지 드러난다.

심은 자리: `server/bugs/validation-behavior.ts`

# N — 이동·라우팅 결함

**내부 이동**만 범위다. 사이트 어디에서도 링크하지 않는 주소는 범위
밖이다 — 링크를 따라가는 도구가 영원히 도달하지 못하기 때문이다.

토글은 `src/bugs/routing/useRoutingBugs.ts` 를 거쳐 읽는다. 화면마다
`useBug("N1")` 을 직접 부르면 ID 가 흩어져서 지울 때 빠뜨린다.

**`N2` 는 비어 있다.** 없는 상품 주소에서 빈 화면을 보여주는 결함이었는데
위 범위에 걸려 뺐다. **번호를 당기지 않는다** — 앞선 커밋에서 `N2` 가
그 결함을 가리켰으므로, 당기면 같은 ID 가 두 가지를 뜻하게 된다.

## N1 — 연관 상품을 누르면 다른 상품이 열림

상품 상세 아래 연관 상품 카드의 이름·사진·가격은 맞는데, 누르면 전혀
다른 컬렉션의 상품이 열린다. 이동은 정상적으로 일어나고 오류도 없다.

`/product/arc-pendant-light` 맨 아래 `You May Also Like` 에서 카드 이름
(`Orb Table Lamp`)을 적어두고 누른다. `Harvest Dining Table` 이 열린다.

**카드에 적힌 이름과 도착한 페이지의 제목을 맞춰보지 않으면 모른다.**
다른 컬렉션의 상품을 목표로 잡은 이유: 같은 컬렉션 안에서 돌리면
컬렉션에 상품이 2개뿐이라 연관 목록이 항상 1건이어서 아무 변화가
없었고, 현재 상품을 가리키면 주소가 그대로여서 화면이 다시 그려지지도
않아 스크롤 결함(N3)과 구분되지 않았다.

심은 자리: `src/pages/ProductDetail.tsx`

## N3 — 화면을 옮겨도 스크롤이 맨 위로 가지 않음

목록 아래쪽에서 상품을 누르면 상세 페이지가 중간부터 보인다. 사진·이름·
가격·담기 버튼이 화면 위로 지나가 있다.

`/products` 를 아래로 충분히 내린 뒤 상품 카드를 누른다.

```js
window.scrollY   // 0 이 아니다
```

**DOM 은 완전히 정상이다.** 달라지는 것은 `scrollY` 숫자뿐이라 규칙 한
줄로 판정되지만, 그 숫자나 스크린샷을 수집해야 보인다. **지금 파이프라인이
그걸 수집하는가** 를 재는 자리이기도 하다.

심은 자리: `src/components/ScrollToTop.tsx`

## N4 — 로그인 후 원래 가려던 곳 대신 홈으로 감

로그인이 필요한 화면에서 로그인하면 그 화면으로 돌아가야 하는데 홈으로
간다. 로그인 자체는 성공하고 오류도 없다.

비로그인 상태로 `/orders` 에 들어가 `Sign In` 을 누르고
`demo@maison.com` / `demo1234` 로 로그인한다. `/orders` 가 아니라 `/` 로 간다.

**세 건 중 이 건만 "가려던 곳" 이라는 이전 상태를 알아야 판정된다.**
도착한 화면(홈)은 그 자체로 완전히 정상이다.

심은 자리: `src/pages/Login.tsx`

# U — UI 결함

필요한 정보를 못 읽게 하거나 조작을 방해하는 표시 문제만 넣는다.
보기 좋고 나쁨은 제외한다. **가림 · 잘림 · 겹침 · 누락**이 기준이다.

다섯 건 전부 `src/styles/bugs-ui.css` 한 파일에서 만든다. 컴포넌트를
고치지 않으므로 다른 분야의 작업과 겹치지 않는다. 켜진 ID 가
`<body data-bugs="U1 U2">` 로 찍히고 CSS 가 `~=` 로 받는다 (`*=` 를 쓰면
`U1` 규칙이 `U12` 에도 걸린다).

> **정상/결함 비교 사진은 [bugs-ui.md](bugs-ui.md) 에 있다.** 창 너비
> 1100px 에서 한 건씩만 켜고 찍은 10장이다. 아래는 증상과 확인 방법만 둔다.

## U1 — 가로 스크롤이 생겨 오른쪽이 잘림

본문 영역이 1280px 아래로 줄어들지 않는다. 창이 그보다 좁으면 넘치는
만큼이 오른쪽 밖으로 나가고 가로 스크롤바가 생긴다. 정렬 상자가
`Featured` 에서 `Fea` 로 잘리고, 헤더 오른쪽의 계정·위시리스트·장바구니
아이콘이 화면 밖으로 밀린다.

```js
document.documentElement.scrollWidth > window.innerWidth   // 1280 > 1100
```

**다섯 건 중 이 한 건만 규칙으로 잡힌다.** 전부 안 잡히면 탐지기 자체를
의심해야 하는데, 이 건이 그 의심을 걷어주는 대조군이다.

## U2 — 상품 이름이 줄임표 없이 잘림

이름이 한 줄로 고정되고 넘치는 부분이 그냥 사라진다. `...` 이 없어서
잘렸다는 사실 자체를 알 수 없다. `Large Sculptural Vessel` 이
`Large Sculptural Ve` 가 된다. 13개 중 10개가 잘리고 짧은 이름
(`Orb Table Lamp`)은 멀쩡해서 더 헷갈린다.

```js
[...document.querySelectorAll('article h3')]
  .filter(el => el.scrollWidth > el.clientWidth).length   // 0 -> 10
```

폭 제한을 `%` 가 아니라 `ch` 로 준 이유: `%` 는 카드 폭에 비례하므로
창을 좁히면 (열 수가 줄어 카드가 넓어져) 증상이 사라진다.

## U3 — 키보드 포커스 표시가 보이지 않음

`Tab` 으로 이동해도 지금 어느 요소에 있는지 화면에 표시되지 않는다.
포커스는 실제로 옮겨가지만 테두리가 그려지지 않아 키보드만으로는
조작할 수 없다.

```js
document.activeElement   // 바뀐다. 그런데 화면에는 아무 표시가 없다
```

**스크린샷으로는 안 보이고 접근성·DOM 쪽으로 봐야 잡힌다.** 탐지 방식에
따라 결과가 갈리는지 보려고 넣었다.

## U4 — 누를 수 없는 버튼이 누를 수 있어 보임

`disabled` 버튼이 흐려지지 않고 손가락 커서까지 떠서 평소 버튼과
구분되지 않는다. 눌러도 아무 일이 없는데 왜 안 되는지 알 수 없다.

`/product/arc-pendant-light` 의 `Quantity` 에서 수량이 1 일 때 `-` 버튼을
본다. 멀쩡한 버튼처럼 보이지만 눌러도 수량이 0 이 되지 않는다.

**F3 과 겉보기 증상이 같다.** 반드시 따로 켠다.

## U5 — 상단 헤더가 본문 첫 부분을 덮음

헤더가 문서 흐름에서 빠져 본문 위에 떠 있다. 모든 화면에서 제목이나
첫 줄이 헤더 뒤에 가려진다. 가려진 영역의 버튼은 눌러도 헤더가 클릭을
가져간다.

`/products` 를 맨 위로 올린 상태에서 본다. `Collection` 제목이 헤더에
가려 보이지 않고, 그 자리를 클릭해도 반응하지 않는다.

| F3 + U4 | 둘 다 수량 `-` 버튼에서 드러난다. 기능 문제인지 표시 문제인지 갈라지지 않는다 |
| F1 + F2 | 둘 다 "담았는데 목록에 없다" 로 보인다. 장바구니와 위시리스트를 혼동하기 쉽다 |
| N1 + N3 | 둘 다 "상품을 눌렀는데 이상한 화면" 으로 보인다. 주소가 바뀌었는지로 갈라야 한다 |
| U1 ~ U5 서로 | 레이아웃이 겹쳐 무너지면 어느 규칙 때문인지 알 수 없다 |

# 탐지 난이도 재평가가 필요하다

레지스트리의 `detectable` 은 **"이렇게 될 것이다"라는 선언**이고 벤치마크가
실제 결과와 대조한다(`server/bugs/types.ts`). 틀려도 되고, 틀린 게
드러나는 것이 측정의 목적이다. 다만 지금 17건 중 15건이 `false` 인데,
코드를 다시 보면 그렇지 않은 것들이 있다.

| ID | 선언 | 다시 본 결과 | 근거 |
|---|---|---|---|
| F1 | `false` | **규칙으로 가능** | 화면의 개수와 카드 개수가 둘 다 DOM 에 있다. 두 숫자 비교 탐지기면 잡힌다 |
| F2 | `false` | **규칙으로 가능** | 성공 토스트와 장바구니 배지를 같이 수집하면 모순이 드러난다 |
| F3 | `false` | **규칙으로 가능** | `needs` 에 이미 `no_state_change` 가 적혀 있고, 그건 `types.ts` 가 범용 수단으로 열거한 값이다 |
| F4 | `false` | 애매 | 무변화는 범용 규칙에 걸리지만, 결함인지 정상인지는 "필터가 걸려 있었는가" 를 알아야 갈린다 |
| V1 | `false` | **규칙으로 가능** | 형식 불량 이메일 제출은 표준 프로브다 |
| V2 | `false` | **규칙으로 가능** | `needs` 가 이미 `state_comparison` 이다. 저장값과 조회값 비교 탐지기면 잡힌다 |
| V3 | `false` | **규칙으로 가능** | 필수 표시 필드 빈값 제출도 표준 프로브다 |
| V4 | `false` | **규칙으로 가능** | 확인 필드 불일치 제출도 표준 프로브다 |
| V5 | `false` | **규칙으로 가능** | 응답이 자기 기준(`minLength: 8`)을 어긴다. 기대 동작을 몰라도 모순이다 |
| N1 | `false` | **규칙으로 가능** | 카드의 이름과 도착 페이지 제목을 비교하는 탐지기면 잡힌다 |
| N3 | `true` | 그대로 | `scrollY` 를 수집하면 규칙 한 줄 |
| N4 | `false` | **그대로 유지** | "가려던 곳" 이라는 이전 상태를 알아야 판정된다. 도착 화면 자체는 정상이다 |
| U1 | `true` | 그대로 | 가로 스크롤 비교 |
| U2 | `false` | **규칙으로 가능** | `scrollWidth > clientWidth` 한 줄 |
| U3 | `false` | **그대로 유지** | 포커스 표시 유무는 계산된 스타일을 봐야 하고, 무엇이 "보이는 표시" 인지 기준이 필요하다 |
| U4 | `false` | 애매 | 흐림 없음은 스타일 비교로 가능하지만, F3 과 구분하려면 원인 판정이 필요하다 |
| U5 | `false` | **규칙으로 가능** | 요소 겹침은 좌표 비교로 가능 |

**아직 레지스트리를 고치지 않았다.** 프로젝트 문서가 지표와 집계 규칙은
평가 전에 고정한다고 정해 둔 만큼, 등급을 어떻게 매길지 먼저 합의한 뒤
`.ts` 를 손대는 것이 맞다. 지금 상태로 측정하면 대부분이 "선언과 달리
규칙으로도 잡혔다" 로 나올 가능성이 높다.

이 표가 말하는 바는 분명하다. **규칙만으로 상당 부분이 잡힌다.** AI 의
값은 탐지율 자체가 아니라 거기까지 **도달**하는 것, 화면마다 수십 개
조작 중 무엇을 **선택**할지, 같은 원인에서 나온 여러 증상을 묶어
**오탐을 줄이는** 것, 그리고 N4 처럼 **기대 동작을 알아야 하는** 소수의
결정적인 건들에 있다.
